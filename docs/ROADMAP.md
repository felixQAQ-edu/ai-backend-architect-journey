## 二、完整路线图

### 第一阶段 · 管道优先，引擎可换 [M1–M2]

**核心理念**：先跑通架构，再替换业务引擎，避免业务复杂度与技术复杂度叠加。

**设计哲学**：前 8 个月（M1–M8）**刻意不锁定业务方向**，是 feature 不是 bug。M1–M2 验证架构通用性，M3–M5 打造赛道无关的通用能力（本地部署、量化、并发），M6–M7 把 RAG 链路做到能用为止。**真正的方向收敛点在 M8 用户验证阶段**——届时手里会有三张牌：技术能力上限、部署成本真实数据、与潜在用户接触后的反馈。用那时的信息做决策，比现在拍脑袋准得多。现在出现的方向直觉一律录入第七节「方向假设池」备查，不做承诺。

**M1 · Spring Boot × LLM 全链路**
- 流式输出（SSE / WebFlux）、会话记忆（ConversationBufferMemory）
- Token 计费中间件，请求/响应日志落库
- Tool Calling 框架：定义 Function Schema，Agent 调用模拟文档检索 API
- 项目交付：团队知识库问答 Agent（Markdown 文档入库）

**M2 · 引擎替换验证架构通用性**
- 把文档检索 API 换成 Yahoo Finance / Alpha Vantage API
- Agent 自动抓取宏观数据，生成简版策略摘要
- 错误处理、重试机制、多轮对话状态管理

**阶段里程碑**：同一套管道代码支撑两个完全不同领域的 Agent，证明架构解耦成功。

---

### 第二阶段 · 底层部署与推理优化 [M3–M5]

**核心理念**：脱离外部 API，真正的架构师壁垒在这里。

**M3 · 本地模型部署**
- Ollama 跑通 Qwen2.5-7B，对比 API 版本的延迟与质量
- vLLM 搭建，理解 PagedAttention 的 KV Cache 内存分配原理
- Java 后端通过 OpenAI-compatible API 接入本地模型

**M4 · 量化技术实验**
- INT8 / INT4 量化对比：模型大小、推理速度、回答质量三维测评
- GGUF 格式与 llama.cpp 在 CPU 上的执行逻辑
- 不同硬件配置（有无 GPU）下的 tokens/s 数据记录

**M5 · 高并发调度**
- Java 线程池 + 请求队列，模拟 50 并发推理压测
- 瓶颈分析：GPU 显存 vs CPU 调度 vs JVM 线程切换
- Batch Inference：合并小请求，观察吞吐量变化

**阶段里程碑**：能解释为什么 13B 模型在 INT4 量化后能跑在 8GB 显存上，精度损失在哪里。

---

### 第三阶段 · Advanced RAG 核心链路 [M6–M8]

**核心理念**：把 AI 做成领域专家，而不是聪明的复读机。

**M6 · 文档解析与语义分块**
- PDF / 代码库 / LaTeX 文档的结构化解析（PyMuPDF、Unstructured）
- Semantic Chunking：基于句子嵌入相似度动态切分
- 父子分块策略（Parent-Child Chunking）

**M7 · 混合检索 Hybrid Search**
- 向量检索（text-embedding-3 / BGE）+ BM25 关键词检索并行
- RRF（Reciprocal Rank Fusion）融合两路排序结果
- 向量数据库选型实验：Milvus vs Qdrant

**M8 · Reranking + 评估 + 用户验证**
- BGE-Reranker-v2 二次打分，对比 MRR@5 提升幅度
- 评估集（50 条真实问答对），跑 RAGAs 量化幻觉率
- **关键节点**：找 5–10 个目标用户真实使用，收集反馈
- **方向决策节点**：拿第七节「方向假设池」所有候选项做并列对比，结合真实用户反馈选定 M9–M12 的最终业务赛道
- **地理决策节点**：同时回答"目标用户主要在哪里"，这与业务赛道一起决定 M9 的部署方案
- **持续性决策节点**：决定回国后是否继续运营本项目——验证好就继续，否则转为简历项目

**阶段里程碑**：RAG 准确率在评估集上达到 80%+，且有真实用户证明"这个东西有用"。

**选修项**：GraphRAG（若 M6–M7 顺利且有 Neo4j 经验，M8 末可探索）

---

### 第四阶段 · 高可用 SaaS 与商业变现 [M9–M12]

**核心理念**：把九个月积累打包成真正能上线赚钱的系统。

**M9–M10 · 分布式架构升级**
- Redis 分布式锁管理并发 Agent 任务
- Kafka 异步队列：长耗时 AI 任务从同步改异步
- 多租户隔离：数据库 Schema 级 + 向量库 namespace 分区
- 监控接入：Prometheus + Grafana

**M11 · 商业闭环**
- Stripe 支付网关 + Webhook 处理订阅状态（悉尼期间用海外信用卡跑通技术链路）
- Token 用量计费：按月订阅 + 超量计费双模式
- 用户仪表板：用量、账单、套餐升级
- **回国后切换微信支付/支付宝**——技术抽象层 100% 复用，详见第八节

**M12 · Tech Lead 统筹上线**
- 灰度发布、线上压测、容量规划
- 运营数据看板：DAU、留存率、MRR
- 完整技术架构文档（简历核心材料）

**最终里程碑**：系统上线，有付费用户，有可量化的业务数据 — 不是 demo，是产品。

### 用户验证渠道备忘（M8 阶段使用）

> 提前记录的低成本传播路径，避免 M8 临阵两眼一抹黑。
> **核心原则**：渠道是产品的乘数，不是加数。产品本身解决真痛点时渠道才有意义。

- **寄生在已有社区**（首选）：去目标用户聚集的鱼塘真实回答问题，顺手提产品。国内：即刻 / 小红书 / 知乎 / V2EX / 少数派；海外：Reddit 对应 subreddit / Hacker News（Show HN）/ Product Hunt / Twitter
- **写"过程"而不是"产品"**：把 ADR 这种深度技术决策做成连载，发掘金 / InfoQ / Medium。简历和影响力双倍收益，产品没做成写作本身也值钱
- **找 10 个不是 1000 个**：M8 阶段目标只是 5–10 个真实用户，朋友圈、群、前同事直接问足够，不用造流量。真正难的是后续找愿意付钱的人
- **冷启动套路**：免费给一个有名的开源项目 / 机构做定制部署，借光被看见（"build in public + lighthouse user"）
- **悉尼远程触达国内用户的具体打法**：微信群/朋友圈 + 在小红书/知乎相关话题下真实回答；如果方向选了"大学生学习助手"，悉尼大学华人留学生群体本身就是潜在用户池

## 七、方向假设池

> 不锁定方向，但**结构化记录**每一次方向直觉。M8 用户验证阶段拿这张表所有候选项做并列对比，结合真实用户反馈做最终决策。开新对话冒出新方向想法时，按下方结构追加一条即可。

### 判断方向的四问框架

每条候选都用这四个问题快速过一遍，全部答得漂亮的方向才是好方向：

1. **我的技术栈（RAG）能在这里发挥到极致吗？** — 离 RAG 越远的场景越不适合
2. **ChatGPT 在这里答不准吗？** — 如果通用大模型已经够用，产品就没意义
3. **这里有没有合规雷区？** — 金融、医疗、法律是三大雷区
4. **用户在哪里？我够得着吗？** — 用户聚集且渠道清晰的方向优先

**金融分析 / 投研助手**
- 趋势支撑：中国年轻一代资产配置觉醒（房产逻辑衰退、存款利率下行、对工资养老的不信任），可能是持续 10 年的结构性机会
- 优势：信息有时效性 + 有结构（财报/研报/公告标准格式）+ 用户付费意愿强（影响投资决策的信息付费意愿是普通知识的 10 倍量级，参考 Bloomberg 终端 24000 美金/年的底层逻辑）
- **隐藏陷阱：合规深水区**。在中国向用户提供"投资建议"需证券投资咨询牌照，回答里禁止出现买卖建议。可绕开但需在产品定位上严格设计为"信息检索工具"而非"决策助手"。M8 用户验证时必须明确测试"产品定位能不能既有用又不踩线"
- 其他风险：高质量数据 API 成本高（Wind / 同花顺）、Yahoo Finance 在 A 股覆盖有限；散户对 AI 的"帮我赚钱"预期会反噬产品口碑；东方财富 / 雪球等平台已在加 AI 功能

**专业考试备考**
- 完美匹配 RAG 的所有特征：内容有边界（指定教材 + 历年真题 + 考纲）、用户焦虑且付费意愿强（一次考试 = 半年到一年的人生节点）、ChatGPT 答不准（专业术语 + 本土考点 + 政策更新）、市场分散无通吃者（每个细分考试都是独立机会）
- 可选细分：CFA / CPA / 法考 / 公务员 / 考研专业课
- 风险：内容版权（教材授权问题）、考纲变化的内容更新成本

**大学生课程学习助手**
- 场景定位：不只是"考前划重点"，是**整个学期的学习陪伴工具**——几十 G 讲义跨文档检索、跨章节知识点串联、精准引用页码
- 用户画像：每年 1000 多万在校生，用户高度集中、渠道清晰（小红书 / B 站 / 校园社群），自己是潜在用户的近邻人群，需求验证不用跑很远
- 技术栈匹配度极高：PDF/PPT 解析（M6 直接对口）+ 跨文档检索（M7）+ 精准引用（M8 最容易出"哇"时刻）
- 头部空白：Notion AI / 夸克都在做相关功能，但都是通用产品的子功能，不是为"中国大学生学习场景"专门设计的垂直产品
- **合规风险最低**，相对金融、医疗、法律方向有明显优势
- **悉尼优势**：身边的悉尼大学华人留学生本身就是潜在用户池，可作为 M8 验证的补充样本

## 八、跨境时间线与迁移检查点

> 本项目在悉尼留学期间启动与开发，2027-06 末回国。
> 目标用户初步定位为中国用户，但所有"商业化基础设施"决策延迟到 M8 验证结果出炉后再做。
> 这是为了避免在不确定方向时做出不可逆投入。
> 详细技术决策见 `ADR-003-cross-border-deploy.md`。

### 部署策略：香港中转

- **M9–M12 开发期**：阿里云/腾讯云香港节点，免 ICP 备案、悉尼访问快、对中国用户延迟可接受（80–150ms）
- **回国后**：根据 M8 验证结果分叉：
  - 验证好且继续运营 → 迁移大陆节点 + ICP 备案
  - 转为简历项目 → 维持香港节点（成本低、不折腾）

### 支付策略：分层设计

- **M11 技术打通**：Stripe（用悉尼海外信用卡测试）— 跑通订阅扣费、Webhook 处理、用量计费的全套链路
- **回国后真实运营**：切换微信支付/支付宝 + 个体户主体
- **关键认知**：技术抽象层（Webhook、订阅状态机、用量记账）100% 复用——简历上是"双通道集成经验"，是真实卖点不是冗余

### 跨境检查点

| 检查点 | 时间 | 必须完成的事 |
|-------|------|------------|
| M8 末 | 2026-12 | 用户验证 + 锁定目标用户地区 + 决定是否继续运营 |
| M9 启动 | 2027-01 | 选定香港云节点、域名（.com 优先）、备份方案 |
| M11 启动 | 2027-03 | 接入 Stripe 跑通技术链路 |
| 回国前 1 月 | 2027-05 末 | 数据备份演练、跨境网络测试、迁移可行性评估 |
| 回国后 1 月 | 2027-07 末 | 根据 M8 决策最终决定迁移或维持 |

### 暂不做清单（M8 验证结果出炉前）

为避免在不确定方向时做出不可逆投入，以下事项**全部延迟**到 M8 验证后再决策：

- ❌ 注册公司主体（个体户/有限公司）
- ❌ ICP 备案
- ❌ 商标注册
- ❌ 长期云服务器套餐（按需付费即可）
- ❌ .cn 域名（.com 优先）
