# ADR-003 · 跨境部署节点与支付通道策略

- **日期**：2026-05-04
- **状态**：已采纳（约束已锁定，具体技术方案 M9 启动前回填）
- **决策者**：Felix

## 背景

本项目的开发周期与开发者本人的地理位置存在一次跨境迁移：

- 项目启动至 M12 上线：2026-04 至 2027-04，开发者在**悉尼**留学
- 回国时间：**2027-06 末**
- 目标用户初步定位：**主要面向中国用户**（M8 验证后正式锁定）
- 回国后是否继续运营：**取决于 M8 用户验证结果**——验证好则继续，否则转为简历项目

这构成一个三层约束：

1. **开发者地理位置**会发生迁移（悉尼 → 国内），但**目标用户地理位置稳定**（中国）
2. 商业化基础设施（公司主体、ICP 备案、商标、支付通道）决策应**延迟到 M8 用户验证结果出炉后**，避免在不确定方向时做不可逆投入
3. 技术架构需要**两边都能跑**——悉尼期间访问要顺畅，对中国用户延迟要可接受

本 ADR 锁定**跨境策略的整体框架与原则约束**。具体技术细节（云服务商、域名注册商、Stripe 接入版本等）在 M9 启动前回填。

## 候选方案

跨境部署与支付通道有四种典型策略：

### 方案 1：全程国内部署（阿里云大陆 + 微信支付）

**优点**：
- 中国用户访问最快、延迟最低
- 微信/支付宝是中国用户主流支付通道，转化率高
- 长期看是最终形态，一步到位无需迁移

**缺点**：
- **ICP 备案需要中国大陆身份证 + 实际办公地址**——悉尼期间办理流程复杂
- 微信支付/支付宝商户号需要**营业执照**，等于现在就要注册公司主体
- 在 M8 验证结果出炉前注册公司主体属于**不可逆投入**——如果方向不行，公司维护成本（年报、税务）会成为持续负担
- 悉尼期间访问大陆服务器有时会受跨境网络波动影响，调试体验不稳定

### 方案 2：全程海外部署（AWS Sydney / DigitalOcean + Stripe）

**优点**：
- 悉尼期间访问最快、信用卡支付便利、Stripe 注册顺畅
- 不需要 ICP 备案、不需要中国营业执照
- 学习"海外 SaaS 标准技术栈"（Stripe、AWS 服务）的简历价值高

**缺点**：
- **中国用户访问慢且不稳定**——国际出口带宽有限，部分用户访问可能受限
- Stripe 不直接面向中国大陆消费者，**实际无法收中国用户的钱**（除非用户本身有海外卡，比例极低）
- 回国后如果继续运营，几乎必须整体迁移——属于"先吃亏后填坑"

### 方案 3：香港中转（阿里云/腾讯云香港 + 阶段性支付通道）

**优点**：
- 香港节点对**两边都不差**：悉尼访问通过国际线路（约 100–200ms），中国大陆访问通过 CN2 GIA 优化线路（约 80–150ms）
- **不需要 ICP 备案**——香港主机豁免备案
- 阿里云/腾讯云香港都支持人民币结算，账单管理方便
- 是中国出海 SaaS 公司的**标准过渡方案**——成熟、可复制
- 保留所有未来路径：M8 验证好可迁大陆，验证一般可维持现状，都不会有沉没成本

**缺点**：
- 对大陆用户延迟比大陆节点高 30–80ms，但对 SaaS 应用（非游戏/直播）完全可接受
- 长期来看略贵于大陆节点（约 1.3–1.5 倍价格）

### 方案 4：双边部署（开发环境海外 + 生产环境大陆）

**优点**：理论上两边都最优

**缺点**：
- 复杂度爆炸：两套环境、两套配置、两套监控
- 对一个学习项目+不确定商业化的状态来说**严重过度设计**
- 直接排除

## 最终决策

**方案 3 — 香港中转策略**，并配套**支付通道分层设计**。

### 部署节点：阿里云/腾讯云香港节点

- M9–M12 开发期与初步上线：**香港节点**
- 回国后根据 M8 验证结果分叉：
  - 验证好且决定继续运营 → 迁移大陆节点 + 启动 ICP 备案 + 注册个体户/公司主体
  - 转为简历项目 → 维持香港节点（成本低、维护简单、不折腾）
- 具体云服务商（阿里云 vs 腾讯云）+ 实例规格选型：M9 启动前回填

### 支付通道：分层设计

| 阶段 | 通道 | 用途 |
|------|------|------|
| M11 技术打通 | **Stripe**（悉尼海外信用卡） | 跑通订阅扣费、Webhook 处理、用量计费完整链路 |
| M11 末用户付费测试 | Stripe（小范围） | 1–2 个海外华人朋友真实付费验证 |
| 回国后真实运营 | **微信支付/支付宝 + 个体户主体** | 中国用户主流通道 |

**核心认知**：M11 的真正学习目标是**"打通支付集成的技术抽象层"**——Webhook、订阅状态机、用量记账、退款流程。这些抽象在 Stripe 和微信支付之间 100% 复用，简历上是"双通道集成经验"，是真实卖点而不是冗余。

### 关键理由

1. **匹配真实约束**：开发者位置在悉尼但用户在中国，香港节点是唯一**对两边都能用**的选择。
2. **保留所有未来路径**：M8 验证结果未出，任何"all in 大陆"或"all in 海外"的决策都是赌博。香港中转策略让所有分叉路径都打开。
3. **避免不可逆投入**：在方向未锁定时不注册公司主体、不办 ICP 备案、不注册商标，避免一旦方向调整产生的清算成本。
4. **Stripe 学习价值**：即使最终切换到微信支付，Stripe 接入经验在简历上是加分项——展示了对海外 SaaS 标准范式的熟悉。

## 已知代价

1. **延迟代价**：香港节点对大陆用户延迟比大陆节点高约 30–80ms。对 SaaS 应用可接受，对实时游戏/直播不可接受——但本项目不是后两者。
2. **成本代价**：香港云服务器价格约为大陆节点的 1.3–1.5 倍。M9–M12 期间预计月支出 ¥150–250（大陆节点同规格约 ¥100–180），增量在可承受范围。
3. **支付通道双重学习成本**：M11 学 Stripe 后回国还要再学一次微信支付。但这恰好是"双通道集成"简历亮点的来源。
4. **数据合规**：如果 M8 验证后决定继续运营且用户量增长，**数据存储位置**会涉及《个人信息保护法》（PIPL）合规要求。届时若用户数据留在香港、用户在大陆，需要重新评估是否触发数据出境申报。M9 多租户隔离设计应预留"按地区隔离数据存储"的能力。

## 跨境检查点（行动时间线）

| 检查点 | 时间 | 必须完成的事 |
|-------|------|------------|
| M8 末 | 2026-12 | 用户验证 + 锁定目标用户地区 + 决定是否继续运营 |
| M9 启动 | 2027-01 | 选定香港云服务商、域名（.com 优先）、初始备份方案 |
| M11 启动 | 2027-03 | 接入 Stripe 跑通技术链路 |
| 回国前 1 月 | 2027-05 末 | 数据备份演练、跨境网络测试、迁移可行性评估 |
| 回国后 1 月 | 2027-07 末 | 根据 M8 决策最终确定：迁移大陆 / 维持香港 / 关停 |

## 暂不做清单（M8 验证结果出炉前）

为避免在不确定方向时做出不可逆投入，以下事项**全部延迟**到 M8 验证后再决策：

- ❌ 注册公司主体（个体户/有限公司）
- ❌ ICP 备案
- ❌ 商标注册
- ❌ 长期云服务器套餐（按需付费即可，不锁年付）
- ❌ .cn 域名（.com 优先，跨境无障碍）
- ❌ 接入大陆 CDN（用云服务商自带 CDN 即可）

## 重新审视的触发条件

- M8 用户验证结果与"目标用户主要在中国"的假设产生显著偏差（例如海外华人占比超 50%）
- 实测香港节点对大陆用户延迟超过 200ms，影响产品可用性
- 中国监管政策对香港主机豁免备案的口径发生变化
- 用户量增长触发 PIPL 数据出境合规审查门槛
- 决定不回国（或回国时间显著推迟）
